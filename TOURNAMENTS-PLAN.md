# План: турниры — что делаем дальше

Рабочий план активной задачи. **Источник правды для следующих чатов**: новый чат по теме турниров
начинает с этого файла и последней записи в `WORKLOG.md`.

**Правило файла: здесь только невыполненное.** Сделанное отсюда вычищается — его история живёт в
`WORKLOG.md`, а принятые решения переезжают абзацем в `ARCHITECTURE.md` / строкой в `CLAUDE.md`.
Иначе следующий чат читает страницы уже неактуального текста и путается.

Первая волна (модель турниров, админка, импорт составов файлом, парсинг и проверки, заявка команды с
сайта) закрыта 22.08.2026 — см. `WORKLOG.md` за эту дату. Ниже — то, что осталось.

## 1. Что помнить при работе (действующие решения)

- **Турнир — контейнер сезона:** дивизион принадлежит турниру, участие команды — строка
  `TournamentEntry` (там же группа и посев). Команда переживает турнир, участие — нет.
- **Зеркала строкой.** `Team.group`, `Series.division`, `GroupEntry.division` дублируют имя
  дивизиона: по ним фильтруют полтора десятка выборок. Источник правды — `divisionId`, единственный
  писатель зеркал — `src/lib/tournaments.ts`. Новый код разрезает данные по `divisionId`.
- **Заявка не пишет в ростер.** `TeamApplication` лежит очередью; `Team`/`Player`/`RosterSpot`
  заводит апрув. Единственный писатель ростера — `writeTeamToRoster`, проверки — `applicationProblems`.
  Исключение — импорт таблицы оператором: он пишет сразу, подтверждать себе нечего.
- **Парсер один** (`src/lib/roster-import.ts`) на все входы: колоночная раскладка, блочная сезонная
  таблица, построчный текст. Сеть (Steam/OpenDota) — отдельным шагом `enrich.ts`, не внутри записи.
- **Ранг из OpenDota пишем в `Player.rank`; ник и аватар — нет**: ник в лиге человек выбирает сам,
  `Player.photo` у нас всегда локальный файл. Оператору показываем справкой.
- Права: всё в админке турниров — под `tournaments.edit`, проверка и на странице, и в server-action.

## 2. Долг, ждущий выката наружу

- **Telegram-бот с квизом.** Бот ведёт капитана по вопросам, ответ ложится в `TeamApplication`
  (`source = telegram`). Нужен публичный адрес под вебхук — до выката (`DEPLOY.md`) делать нечего.

## 3. Этапы — вторая волна (собрана 23.08.2026)

Список собран Стасом по итогам живого заведения турнира. Порядок — от быстрых блокеров к крупной
перестройке; каждый пункт = отдельный чат (или `stage`), в конце `ship`. Отмечать статус здесь же.

**Размер этапа — под один чат.** Держим правило: этап должен укладываться примерно в **половину
контекста** чата, включая чтение этого плана и последней записи журнала. Крупные этапы поэтому
разбиты на подэтапы (Э8a/b/c и т.п.) — каждый подэтап это отдельный чат со своим `ship`, а не
«сделаем сколько успеем». Если по ходу видно, что не влезаешь: доделай текущий подэтап целиком,
запиши в журнал, где остановился, и начни новый чат — не дожимай на остатках контекста.

Метки: **S** — правка на один-два файла, **M** — раздел целиком, **L** — так не берём, дробим.
«⚠️ решить до старта» — этап нельзя начинать, пока Стас не ответит на вопрос в его тексте.

Зависимости: Э9 (регистрация капитаном) — после Э8, она продолжает ту же цепочку. 

### Э8 — мастер создания турнира (квиз) ⬜ · L → три подэтапа

Создание турнира — пошаговым мастером: Описание → Дивизионы → Импорт составов → Жеребьёвка. Каждый
шаг отдельным экраном с «назад»/«дальше» и сохранением прогресса (черновик создаётся на первом шаге).
«Заявки команд» из цепочки убрать — отдельная логика. Существующая карточка турнира остаётся для
правки.

- **Э8a · каркас мастера.** Роут `/admin/tournaments/new/[step]`, состояние шага (черновик турнира в
  БД + номер шага в URL), навигация «назад/дальше», выход в карточку турнира. Внутри шагов — пока
  существующие формы как есть.
- **Э8b · шаги «Дивизионы» и «Импорт составов»** переносятся в мастер: та же логика, разложенная по
  экранам, с переходом дальше только когда шаг осмысленно завершён.
- **Э8c · шаг «Жеребьёвка» и финиш.** Развод по группам внутри мастера, финальный экран «турнир
  готов» со сводкой и ссылками. Заявки команд из цепочки убраны окончательно.

### Э9 — регистрация команды капитаном ⬜ · L → два подэтапа · после Э8

Турнир заведён — дальше сезон наполняют не операторы, а капитаны: собрать ростер и подать заявку на
участие. Сегодня есть только заготовка `/tournaments/<slug>/apply` (`apply-form.tsx`,
`src/lib/team-application.ts`), её надо довести до настоящего флоу.

**Решено (Стас, 23.08.2026):**
- **Подать может любой вошедший аккаунт**, даже в статусе `draft`: капитан новой команды часто сам
  ещё не в лиге, а заявка всё равно проходит модерацию — второй фильтр на входе только мешал бы.
- **Команду можно завести прямо в заявке** (название, тег, логотип). `Team` создаётся только при
  апруве, до этого живёт в payload — то же правило, что с игроками.
- **Одна заявка на команду в турнире.** Повторная подача открывает существующую на правку, а не
  плодит строку в очереди.
- **Капитан — тот, кто отмечен в составе**, а не автоматически подавший: заявку может отправлять
  менеджер, который сам не играет.

Остальное к реализации:
- **Как собирается состав.** Игрок из ростера — поиском по нику; **новичка, которого в БД нет**,
  капитан добавляет прямо в заявке (ник + ссылка на профиль + заявленный MMR + роль). Такой игрок
  `Player` не заводит — он часть payload'а `TeamApplication` и появляется в ростере только при
  апруве (то же правило, что в анкете кабинета: `Player` создаёт апрув, не форма).
- **Что проверяем на лету:** ссылка → `account_id`, игрок уже действующий в другой команде
  этого дивизиона, дубль по `account_id` под другим ником, занятый слаг команды, размер состава,
  порог MMR дивизиона. Всё это уже есть в `applicationProblems` — форма должна показывать проблемы
  капитану **до отправки**, а не отдавать их модератору.
- **Куда попадает.** В очередь `TeamApplication` (`source = web`) и в модерацию: карточка заявки с
  составом, распознанными id, проблемами; решения — одобрить (заводит команду, игроков, состав,
  участие в дивизионе) или вернуть с причиной, которую капитан видит и правит.
- **Что видит капитан после подачи:** статус заявки в кабинете, причина возврата, возможность
  дослать правки, а не подавать заново.
- **Приёмка:** капитан с нуля (команда и двое новичков не в БД) проходит регистрацию, модератор
  одобряет, команда встаёт в дивизион со всем составом; повторная подача той же команды не плодит
  дублей.

- **Э9a · форма капитана.** Сбор состава (поиск по ростеру + новички вручную), проверки до отправки,
  подача в очередь.
- **Э9b · модерация и обратная связь.** Карточка заявки у модератора, апрув/возврат с причиной,
  статус и досыл правок в кабинете капитана.

### Э12c — архив серий: источник id матчей ⬜ · M · готов к старту

`/admin/series` (`page.tsx` + `_components/series-admin.tsx`, логика — `src/lib/series.ts`).

- **Ссылка на внешний источник матчей — у турнира.** Смысл (решено 23.08.2026): не справка для
  оператора, а **источник id матчей** для заполнения архива. Где эти id лежат — предмет опыта:
  Liquipedia, Dotabuff, возможны альтернативы. Поэтому Э12b начинается с разведки источников (что
  реально отдаёт список матчей турнира и в каком виде), и только потом пишется разбор. Поле живёт
  у турнира, не у встречи.
- **Приёмка:** оператор с главной страницы архива попадает в нужный турнир за один клик, привязывает
  карту и перечитывает её, не видя чужих сезонов; свёрнутый список встреч читается без прокрутки.

- **Э12c · источник id матчей (разведка + разбор).** Проверить на живых турнирах, откуда реально
  берётся список матчей — Liquipedia, Dotabuff, альтернативы; что из этого доступно программно и
  насколько стабильно. Итог разведки записать сюда, затем поле-ссылка у турнира и подстановка id в
  привязку карты вместо ручного ввода. Отдельный чат: это эксперимент, а не понятная правка.
