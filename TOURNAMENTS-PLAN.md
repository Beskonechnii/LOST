## 1. Что делаем

Требования, с которых всё началось (формулировка Стаса):

1. Модерация **заводит турниры руками**: создать турнир, описать его (регламент, даты, формат, призы).
2. Внутри турнира — **дивизионы и команды**: составы заводятся не скриптом с ноутбука, а из админки.
3. Источник составов — **файл с данными о командах** (xlsx/csv/гугл-таблица), позже — **рега через
   Telegram** с квизом по заранее составленным вопросам.
4. Главное — **минимальная ручная работа**: всё, что можно вывести из данных (account_id из ссылок,
   ранг, дубли, конфликты составов), выводится автоматически и показывается оператору до записи.

Развилки, пройденные до кода (ответы Стаса 22.08.2026):

- Турнир — **полноценная сущность БД**, дивизионы внутри него, существующий S2 мигрируем.
- Первый вход данных — **импорт файла в админке**. Веб-форма капитана и TG-бот — позже.
- Импорт **не пишет в ростер напрямую**: заявка → апрув → `Team`/`Player`.
- Парсим автоматически: **ссылки → account_id**, **OpenDota (ранг, ник, аватар)**, **дубли и конфликты
  составов**. MMR из файла остаётся заявленным (как в анкете кабинета — подтверждает оператор).

## 2. Ключевые решения

### 2.1 Турнир — сущность, дивизион — его часть

Сейчас дивизион это строка `"Division 1"` в `Team.group`, `Series.division`, `GroupEntry.division`
плюс хардкод-справочник `src/lib/divisions.ts`. Пока лига — один сезон с двумя дивизионами, это
работало; «заводить турниры руками» на строках не делается — описание, даты и регламент вешать некуда,
а второй сезон с теми же именами дивизионов склеится с первым.

Поэтому: `Tournament` (сезон/кубок) → `Division` (D1/D2 внутри него) → `TournamentEntry`
(участие команды в дивизионе турнира). `divisions.ts` из хардкода становится выборкой из БД,
сигнатуры (`divisionBySlug`, `divisionSlug`) сохраняются — иначе правка расползётся по 14 файлам сразу.

### 2.2 Участие команды — отдельная строка, а не поле у команды

`Team.group` («в каком дивизионе команда») заменяется на `TournamentEntry`. Причина простая:
команда живёт дольше турнира. Со строкой в `Team` переход на S3 стирает, где команда играла в S2;
со строкой участия история копится сама, а «команды дивизиона» — это `where divisionId`.

Состав (`RosterSpot`) в этом плане **не сезонится** — остаётся текущим составом команды. Сезонные
составы — известный долг (§9 `CLAUDE.md`), и тянуть его сюда значит переписать заодно ростер, студию
и драфт. Историю игр это не рвёт: `MatchStat` уже хранит, кто играл на карте.

### 2.3 Заявка не создаёт `Team` (как в плане аккаунтов)

Импорт файла и любая будущая рега создают `TeamApplication` — состав целиком JSON'ом, как
`UserAccount.application`. `Team`/`Player`/`RosterSpot` пишутся **только при апруве**.

*Почему.* Публичные витрины читают `Team`/`Player` без фильтров (`ACCOUNTS-PLAN.md` §2.1, та же логика).
Кривой файл, залитый сразу, немедленно виден на `/roster/teams`, а откатить upsert по 12 командам
нечем. Заявка же лежит сбоку и ничью выборку не трогает.

### 2.4 Разбор — до записи, с проблемами списком

Импорт двухшаговый: **разобрать и показать** (что за команды, кто в составах, что не распозналось,
где конфликт) → оператор чинит спорное прямо в превью → **записать**. Ошибки разбора не молчат: игрок
без account_id, дубль ника, команда с занятым slug, игрок уже действующий в другой команде этого
дивизиона (`roster-spots.ts`) — всё выводится строками с пометкой «блокирует / предупреждение».

### 2.5 Парсер один, входов много

Разбор состава живёт в `src/lib/roster-import.ts` — **чистый модуль** (без БД и `next/headers`):
таблица/JSON → `RosterDraft`. Его зовут: страница импорта в админке, существующие скрипты
(`sheet-to-roster.ts`, `import-roster.ts`) и будущий TG-бот. Иначе к третьему входу будет три
разных представления о том, что такое «состав».

Читалка xlsx (`scripts/xlsx.ts`) переезжает в `src/lib/xlsx.ts`, скрипт остаётся реэкспортом.
Конвенция «скрипты в рантайм не тянуть» не нарушается — движение ровно в обратную сторону.

### 2.6 Обогащение — отдельный шаг, а не побочный эффект

`account_id` из ссылок (`profiles.ts`), именной адрес Steam через `STEAM_API_KEY`
(`resolve-vanity.ts`), ранг/ник/аватар из OpenDota — это **сеть**, а сеть в форме сохранения означает
таймаут посреди записи. Поэтому обогащение — явная кнопка на превью («подтянуть данные»), результат
падает в черновик заявки, запись идёт уже офлайн.

### 2.7 Право `tournaments.edit`

Новый ключ в `src/lib/permissions.ts`, группа «Турнир» (рядом с `series.edit` и `tp.edit`). Проверка —
на трёх уровнях, как заведено этапом 4 плана аккаунтов: `proxy` (роль) → страница
(`denyUnlessPermission`) → пишущий роут (`guard`). Апрув заявки команды требует **и** `tournaments.edit`,
**и** `roster.edit`: он заводит записи в ростере.

### 2.8 Снимок БД — версия 12

`Tournament`/`Division`/`TournamentEntry`/`TeamApplication` едут в `data/snapshot.json`. Связи по slug,
как везде. Импорт старой версии (11) отвергается — это уже поведение `import-db.ts`.

## 3. Модель данных

```prisma
model Tournament {
  id          Int      @id @default(autoincrement())
  slug        String   @unique // s2, s3, winter-cup — живёт в URL
  name        String            // «LOST Season 2»
  short       String?           // «S2» — для навигации
  description String?           // регламент/описание, длинный текст
  format      String?           // «2 дивизиона, группа + плей-офф»
  prize       String?
  logo        String?
  banner      String?
  status      String   @default("draft") // draft | registration | running | finished
  startAt     DateTime?
  endAt       DateTime?
  regOpenAt   DateTime?
  regCloseAt  DateTime?
  createdAt   DateTime @default(now())

  divisions    Division[]
  applications TeamApplication[]
}

model Division {
  id           Int    @id @default(autoincrement())
  slug         String            // d1 — уникален внутри турнира
  name         String            // «Division 1»
  label        String?           // «LOST D1»
  short        String?           // «D1»
  orderNo      Int    @default(0) // порядок вкладок
  mmrFrom      Int?              // порог входа, если есть
  mmrTo        Int?
  tournament   Tournament @relation(...)
  tournamentId Int
  entries      TournamentEntry[]
  @@unique([tournamentId, slug])
}

model TournamentEntry {   // участие команды в дивизионе турнира
  id         Int @id @default(autoincrement())
  division   Division @relation(...)
  divisionId Int
  team       Team @relation(...)
  teamId     Int
  seed       Int?     // посев/номер в жеребьёвке
  group      String?  // «A» | «B» — жеребьёвка группы
  createdAt  DateTime @default(now())
  @@unique([divisionId, teamId])
}

model TeamApplication {   // заявка команды: состав целиком JSON, Team не создан
  id           Int @id @default(autoincrement())
  tournament   Tournament @relation(...)
  tournamentId Int
  divisionId   Int?      // предложенный дивизион; оператор может переставить
  source       String    // import | web | telegram — откуда пришла
  payload      String    // JSON: команда + игроки + сырые ответы (src/lib/team-application.ts)
  status       String @default("pending") // pending | approved | rejected
  notes        String?   // причина возврата
  submittedAt  DateTime @default(now())
  reviewedAt   DateTime?
  reviewedById Int?      // след в истории, без relation — как в UserAccount
  teamId       Int?      // проставляется при апруве
}
```

Правки существующих моделей:

- `Team.group` (строка) → удаляется после миграции; «дивизион команды» = `TournamentEntry`.
- `Series.division`, `GroupEntry.division` (строки) → `divisionId` FK. Строки живут параллельно один
  этап, чтобы миграция не была ночным прыжком: сначала FK заполняется, потом код переключается, потом
  колонка уходит.
- `Player.rank` (`Int?` или строка медали) — если тянем ранг из OpenDota (этап 4).

## 6. Вторая волна — правки после первого прогона (23.08.2026)

Список собран Стасом по итогам живого заведения турнира. Порядок — от быстрых блокеров к крупной
перестройке; каждый пункт = отдельный чат (или `stage`), в конце `ship`. Отмечать статус здесь же.

### Э1 — три быстрых бага ⬜

Починить: (1) после регистрации игрока клик по профилю ломает страницу — воспроизвести, найти
причину (вероятно, `Player` ещё не заведён: он создаётся только при апруве, `src/lib/account.ts`),
показать внятное состояние вместо падения; (2) на `/admin/tournaments/<slug>` кнопка «Сохранить» в
блоке «Описание» не даёт обратной связи — видимый pending + подтверждение; (3) вернуть кнопку/плитку
«Админ» на главную (`src/app/(public)/page.tsx`, `src/app/_components/hub-tiles.tsx`) — видна только
админам, как вкладка в шапке.

### Э2 — распознавание account_id из ссылок ⬜

`accountIdFromUrl` (`src/lib/profiles.ts`) берёт не все ссылки Dotabuff (пример — Hobbits): регексп
ждёт ровно `dotabuff.com/players/<id>`, а в жизни бывают `ru.dotabuff.com`, хвосты `/matches`,
`/overview`, локали. Расширить разбор всех источников (dotabuff/stratz/opendota/steam), покрыть
варианты, а в мастере импорта показывать оператору строки, где id не распознан.

### Э3 — команды не видны в дивизионе нового турнира ⬜

В новом турнире команды показываются только в группе «ВСЕ», в самом дивизионе пусто. Разобраться, по
чему фильтруют публичные витрины (`src/app/(public)/tournaments/[slug]/…`, `divisionTeams`, зеркало
`Team.group` против `TournamentEntry.divisionId`) и вести разрез по `divisionId`, а не по строке.

### Э4 — плей-офф только после группы ⬜

Сейчас команды попадают в сетку сразу из текущих позиций группы. Участники должны подставляться
только после завершения групповой стадии (нужен явный признак: статус стадии дивизиона либо «все
встречи группы сыграны»), до этого — слоты-заглушки. Файлы: `src/lib/qualification.ts`,
`group-stage.ts`, `playoff/_components/bracket.tsx`.

### Э5 — история составов в профиле команды ⬜

Состав меняется от турнира к турниру (`RosterSpot.divisionId`). На карточке `/roster/teams/<id>` —
текущий состав турнира и ниже прошлые составы по турнирам: название турнира, дивизион, игроки с
ролями, итог участия, если есть.

### Э6 — модерация: «Регистрации» + «Заявки» в один раздел ⬜

«Регистрации» → «Регистрация личного профиля», объединить с «Заявки» (`/admin/registrations`,
`/admin/claims`) в один раздел с внутренними вкладками. На плитке `/admin` и на вкладке —
небольшой цветовой индикатор с числом новых, чтобы не пропустить.

### Э7 — «Команда лиги»: роли и раскрывающиеся права ⬜

На `/admin/staff` развести в UI назначаемые роли (владелец / админы / остальные) и сделать блок прав
сворачиваемым (по умолчанию свёрнут) — чекбоксов много, страница длинная.

### Э8 — мастер создания турнира (квиз) ⬜

Создание турнира — пошаговым мастером: Описание → Дивизионы → Импорт составов → Жеребьёвка. Каждый
шаг отдельным экраном с «назад»/«дальше» и сохранением прогресса (черновик создаётся на первом шаге).
«Заявки команд» из цепочки убрать — отдельная логика. Существующая карточка турнира остаётся для
правки. Делать **последним**: трогает то, что чинят Э2–Э4.
